# RGB-D 存档：输入管道与文件系统对照

2026-11-02。run26 已完成 6 个导航目标，但第 6 个观察窗口触发 `writer_wall_timeout`。5 秒期限覆盖 helper 启动、调度、输入传输、checkpoint/文件写入和完成回执；当时失败样本目录尚不存在，不能直接认定为图像文件写盘慢。

## 离线对照

使用 run26 第 5 个完整存档窗口的同一批三组 640×480 RGB-D，逐字节核对输入。失败窗口的原图没有保存，不能声称精确重放失败的第 16 帧。所有组保持已安装 helper 和协议包导入位置、50 ms owner 轮询、每次最多 1 MiB 传输以及 5/10/8 秒期限；不启动 ROS/Gazebo。比较当前 `/mnt/c` 输出与 WSL 原生 ext4，以及默认管道与请求 1 MiB 管道。

| 轮次及顺序 | 输出 | 实际输入管道 | 三帧取得持久化回执 | 文件重读 |
|---|---|---:|---:|---|
| 首轮 1 | `/mnt/c` | 64 KiB | 8.307 s | 通过 |
| 首轮 2 | ext4 | 64 KiB | 请求超时 | 失败，缺帧保留 |
| 首轮 3 | ext4 | 1 MiB | 7.379 s | 通过 |
| 首轮 4 | `/mnt/c` | 1 MiB | 2.891 s | 通过 |
| 反序轮 1 | `/mnt/c` | 1 MiB | 4.815 s | 通过 |
| 反序轮 2 | `/mnt/c` | 64 KiB | writer 超时 | 失败，缺帧保留 |

首轮 `/mnt/c` 默认管道各帧输入发送队列清空耗时约 1.905 / 2.086 / 2.055 秒，扩容组约 0.700 / 0.680 / 0.526 秒。这是父端写入管道的观测，不代表子进程已经读完或完成 fsync。表中三帧耗时从首次请求起算，不包括预热和最终关闭。实际容量均由内核回读，不从单次 write 大小推断。所有自有 helper 均已退出；失败结果未重试覆盖。原始报告、输入哈希、执行脚本与旧模块副本见 [隔离实验档案](../experiments/writer-pipe-20261102/README.md)。

这两轮支持优先改善输入传输余量，单独迁移输出目录没有稳定收益。样本很少，执行顺序、缓存和系统调度未完全隔离，也没有并发仿真负载；不能声称已唯一确定 run26 根因或保证长期无超时。

## 最小实现

在现有 helper 已取得 pidfd 并设置非阻塞管道后，尝试把 stdin 管道容量增至 1 MiB；已有足够容量时不缩减。读取实际容量，权限不足或不支持时保留原管道继续执行，不改变子进程所有权或抛出新的存档故障。Linux 对容量调整有内核和用户限额，详见 [Linux F_GETPIPE_SZ/F_SETPIPE_SZ](https://man7.org/linux/man-pages/man2/F_GETPIPE_SZ.2const.html)；Python 的接口支持见 [fcntl 文档](https://docs.python.org/3.12/library/fcntl.html)。

每次 owner tick 的 1 MiB 传输上限、非阻塞操作、单个受控 writer、5 秒 writer / 10 秒请求 / 8 秒关闭期限均保留。新增固定大小的诊断字段：初始/实际管道容量、调优错误、总/已发/剩余字节、背压次数、首末进展时间、stdin 关闭时间和最大 poll 间隔；不逐帧累积无限时间序列。

run27 继续使用原 Windows 挂载输出目录、run26 的 TF 参数和严格原图留存，验证完整仿真中的表现。此次没有关闭留存检查来换取实验通过。

## 本地验证

新增 10 项管道模拟测试在 Windows 与 Linux 均通过。Linux 原有 adapter/owner 回归与新增测试合计 36 项，在不加载 ROS 搜索路径的纯 Python 环境全部通过（27.585 s），测试断言与期限未修改。

此前两次继承 ROS overlay 的整组执行分别出现 3 个和 2 个断言失败；中间单独复跑两项信号方法通过。第二次捕获的一次失败仍在导入 `pathlib → urllib.parse → ipaddress`，尚未进入 adapter，即超过测试 harness 的 4 s 就绪期限；另一次最终 checkpoint 未及时持久化，现有记录不足以单独归因。所有失败、诊断及后续通过日志一并保留于档案 `validation/`，不能把后续通过当作原失败不存在。

## 主任务与存档的边界

课程要求完整探索、目标标注和返航，不要求每次导航必须等三组原图持久化。现有 `require_retained_inspection` 是默认关闭的专项诊断选项；`require_processed_inspection` 和目标观测校验独立存在。普通自主运行可用已实现的处理证据模式，严格原图存档继续作为独立实验。但任何证据缺失都应明确报告，不能计作完整视觉搜索验证。此次为与 run26 对照，保留严格选项。
