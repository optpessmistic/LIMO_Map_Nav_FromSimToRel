# LIMO 未知迷宫：自主探索、目标感知与返航调研

调研日期：2026-10-28。用户与课程 PPT 已确认 ROS2，正式要求完整探索建图、搜索数量和位置未知的多个目标、在地图中标注、最后返航，不拿取。开发机为 WSL Ubuntu 24.04，采用 Jazzy/Harmonic；实车 ROS2 发行版、相机型号与物品待定。本报告中的上游调研本身不是本项目复现证据，实际运行状态见验证报告。

## 结论与推荐组合

已有成熟的建图、导航、前沿探索和标记识别组件，适合组合实现本实验；没有必要自行重写 SLAM 或路径规划。本次也找到了 LIMO 上的相近项目，但尚未核实一个可以直接复现“未知迷宫、完整建图、指定目标确认、成功返航”的一体化仓库。

开发机当前选择 **Jazzy + Harmonic LIMO 模型 + SLAM Toolbox + Nav2 + 项目任务管理器**。现有 `m-explore-ros2` 的单车 explore_lite 是重要复用和对照候选；本项目首版使用一个受同一任务节点管理的前沿候选选择器，避免探索和返航客户端争夺控制权。目标尚未定义，先以红色 RGB-D 仿真替身验证观测接口，再按实际目标选择 AprilTag 或学习式检测。实车若运行 Humble，则单独适配其驱动和接口，不能直接重装小车或假定跨发行版兼容。

若实车必须保留 ROS 1，则采用官方已经可用的建图组件、`move_base`、ROS 1 `explore_lite` 和 ROS 1 AprilTag 包。ROS 1 与 ROS 2 的包、消息、启动文件和 Action 接口不能直接混用。

建议的任务层流程为：

```text
系统就绪 → 保存起点 → 自主探索＋沿途视觉观察
                    ↓ 疑似目标
                  暂停探索 → 确认旧导航目标取消 → 原地/近距离复核
                    ├─ 误检 → 恢复探索
                    └─ 目标确认 → 根据任务模式继续建图或返航
探索终止 → 检查未完成区域和视觉盲区 → 满足完成条件 → 导航回起点
                                                     ↓
                                               实际到达验证 → 保存结果
```

本项目不需要抓取；目标被确认后应保存观测，继续完成可达空间建图和必要的视觉搜索，再返航。标注作为地图上的独立图层和数据记录保存，不改变占据栅格。

## SLAM、探索与视觉搜索是三件事

**SLAM**根据传感器和运动估计生成地图并估计小车位置；**导航**执行一个给定目标；**探索**根据已知自由空间与未知空间的边界产生新目标。只启动 SLAM 和 Nav2，小车不会自动决定把迷宫走完。上游探索包及 SLAM 包的职责可分别见 [m-explore-ros2](https://github.com/robo-friends/m-explore-ros2) 和 [SLAM Toolbox](https://github.com/SteveMacenski/slam_toolbox)。

以下是本项目需要补充的工程设计：

- 激光看过的区域，不一定被摄像头有效观察过。雷达扫描平面、视野、距离和目标识别所需像素数不同；远处雷达已测到的走廊仍可能藏有视觉目标。
- 维护两个独立状态：地图可通行区域的探索状态，以及相机在有效距离、有效视角下的观察覆盖状态。占据栅格由未知变已知，不能直接把该位置标为“已搜索目标”。
- 在岔路口、死胡同、探索航点及需要补看的位置安排视觉观察。差速模式可在确认旋转空间足够时分步转向；阿克曼模式不能套用原地旋转动作。
- 在低速行驶时持续检测，在关键位置停稳采样。检测频率低于需要时，应降低行驶速度、增加停留或缩短观察点间距。
- 如果地图已充分探索但未找到目标，应执行视觉补查，再输出“已搜索范围内未发现”；不能直接声称物品不存在。

## 任务控制权与取消确认

本项目应只有一个任务管理器决定当前是探索、目标复核、接近目标还是返航。Nav2 负责路径执行；其他节点不得同时争发目标或直接向底盘发速度。人工遥控/急停可以作为更高优先级的明确控制来源。

当前 `m-explore-ros2` 主分支的[探索源码](https://github.com/robo-friends/m-explore-ros2/blob/main/explore/src/explore.cpp)有两个重要行为：手动暂停时先发布 `EXPLORATION_PAUSED`，再调用异步取消；自动探索结束后的返航也在异步取消调用之后立即提交。因此，**暂停状态消息不是导航取消完成的 ACK**，简单地“发 False，再马上发返航”会产生竞争风险。

建议适配方式：

1. 先让探索器停止生成新目标，并把任务状态置为暂停中。
2. 由拥有探索目标句柄的客户端请求取消，等待取消响应，并确认目标进入终态；取消响应与最终 `CANCELED` 是两个需要处理的阶段。
3. 在有限超时内核对不存在尚在执行的旧目标；超时则进入可诊断的故障状态，不启动新的自主运动。
4. 取得导航控制权后再发复核、接近或返航目标，保存新目标 UUID，忽略过期回调。
5. 将探索包的 `return_to_init` 设为 `false`，由任务管理器统一管理返航、失败重试和完成判定。

可以为探索器增加一个在取消完成后才返回的暂停服务，或在自有适配层实现上述协议。`BasicNavigator.cancelTask()` 不能被假定会取消另一个节点私有的目标句柄。对 `/cmd_vel` 观察到零速度也不能单独证明旧导航目标已取消。Nav2 任务调用方式见[官方 Commander 文档](https://docs.nav2.org/jazzy/configuration_and_development/simple_commander_api/simple_commander_api/)。

## 不把所有 frontier 被拉黑误判为完整建图

当前上游探索源码在两种情况下均发布 `EXPLORATION_COMPLETE`：未找到 frontier，以及所有候选 frontier 都被尝试/拉黑。因此，这个消息只能触发**任务层检查探索终止原因**，不能直接满足完整建图验收。来源：[Explore::makePlan](https://github.com/robo-friends/m-explore-ros2/blob/main/explore/src/explore.cpp)。

建议任务管理器分别记录 `no_frontier`、`all_blacklisted`、`navigation_failed`、`timeout`、`target_found` 和 `operator_stop`。若现有状态消息无法区分前两者，应增加结构化原因或读取适配层状态，不依赖解析人类日志文本。

完整建图的检查应包括：地图持续更新且 TF 正常；在预先声明的探索边界和目标地图分辨率内，没有尚未处理的可达未知区域；没有因导航失败而遗留的可达分支；一段稳定时间内满足这些条件。黑名单可以按原因、地图变化和重试次数受控重试，不能无界循环。

仿真中可用已知世界真值离线计算可达区域覆盖率，世界真值不应作为机器人探索输入。实机没有全图真值时，要通过实际场地测量、录像及未完成区域记录辅助验收，报告能力范围，避免宣称算法证明了全图完整。

## 目标识别与定位

**第一阶段建议使用贴在物品上的唯一 AprilTag/ArUco**，前提是实验允许人工标记。它能明确区分目标身份，使自主运动闭环的验证不受训练数据不足影响。配置必须包含指定 ID、字典/家族、实际边长、相机内参和相机至底盘外参。标签需要处于相机可见高度且不被物体自身遮挡。AprilTag 的姿态估计和同步输入约束见 [ROS 2 包说明](https://github.com/christianrauch/apriltag_ros)。

项目应增加以下确认逻辑：指定 ID 连续多帧出现；有效时间窗口内重复观测位置一致；拒绝过旧、无对应 TF 或质量不合格的观测；保存证据图像、检测时间和位姿。帧数、质量阈值、距离上限由仿真和实机采样确定，不把任意数字当作普适阈值。

若目标不能贴标签，再采用适合车载算力的检测模型与 RGB-D。二维框只表明图像中有目标，不能直接作为地图坐标；需要深度对齐、有效深度筛选、相机投影和带时间戳的 TF。深度单位尤其要核实，`16UC1` 通常表示毫米，`32FC1` 表示米；对应 ROS 组件规范见 [depth_image_proc](https://github.com/ros-perception/image_pipeline/blob/rolling/depth_image_proc/doc/components.rst)。

本项目的定位建议是：在目标掩膜或框的内缩区域取稳健深度，剔除无效值与背景；用正确的相机模型计算三维点；使用**采样时间**的相机到地图 TF；融合多次观测并保留不确定性。仅取检测框中心像素的深度容易落到背景，运动时采用最新 TF 也可能造成错位。

如果只要求“找到并返航”，确认有效观测后可不接近物体；若要求到达附近，则生成距物体有余量、位于自由空间且可规划到达的停靠点。不能直接把物体中心当车体导航目标。

## 起点保存、闭环优化与返航

启动后等待传感器、地图和 TF 稳定，保存 `map` 中起点的 `x/y/yaw`、时间戳及任务/地图标识；不要默认起点就是 `(0,0,0)`。返航使用当前地图规划，并保留 SLAM/定位与避障功能。不要简单倒放出去时的速度指令。

ROS 坐标约定区分：`odom` 连续但会漂移，`map` 用于长期全局参照但位姿估计可能跳变。来源：[REP 105 原始文本](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst)。据此，本项目还需处理闭环优化后的地标一致性：

- 首版可在地图初始锚定稳定后保存起点，用地图坐标返回起点邻域，再通过起点标记或实测区域确认实际到达。
- 若使用的 SLAM 允许取得优化后的关键帧/子图位姿，可把起点与目标观测绑定至对应关键帧/子图，优化后重新计算地图中的位置。需要实现并验证这层关联，单独保存一个 PoseStamped 不会自动获得该能力。
- 起点物理标记可用于最后一段对准与验证，也能发现地图误差。对齐动作仍必须经过碰撞检查和明确的控制权切换。
- 不能把历史起点的 `odom` 坐标反复乘以“当前 map→odom”就视为修正完成；当前校正不一定正确描述旧时刻的累计里程计误差。
- 地图重置、SLAM 重启或重新加载地图后，旧的起点和目标记录应失效或经过明确的坐标关联恢复；不能悄悄在新地图里复用旧数值。

## 两种任务模式与真实完成判据

需求必须区分以下模式，建议做成配置项并分别报告实验结果：

| 模式 | 目标确认后的行为 | 成功含义 |
|---|---|---|
| 找到即返航 | 停止探索，保存当前部分地图，导航返回 | 找到指定目标且实际返航成功；不代表完整建图。 |
| 完整建图＋目标搜索＋返航 | 保存目标证据，继续满足建图与视觉搜索要求，再返航 | 建图验收、目标确认、返航验收全部通过。 |

正式实验运行第二种；第一种只用于调试和对照。实验成功至少同时满足：

1. 目标身份和观测证据通过确认，未把疑似检测当成功。
2. 对要求全图的模式，地图完成条件及未处理区域检查通过；地图终止消息本身不足够。
3. 返航 Action 明确成功，且当前位姿/物理起点验证满足位置、角度容差，并保持短时间稳定停止。建议起始验收候选值为位置误差不超过 0.15 m、角度误差不超过 15°，最终阈值需按场地和定位性能确认。
4. 没有碰撞、越界或任务失控；地图和任务记录已保存。

结果应区分：成功、找到目标但返航失败、建图不完整、视觉覆盖未完成、覆盖范围内未发现目标、定位失败、超时、人工中止。最低记录项包括任务模式、ROS/软件版本与提交号、地图、起点和目标观测、状态转换、导航失败原因、轨迹、耗时、覆盖指标、返航误差及人工干预次数。

## 最小验证顺序

1. 固定小场地：验证 TF、手动建图、单目标导航和回起点。
2. 不带目标：验证未知迷宫前沿探索，专门制造窄通道、死胡同和不可达 frontier，确认终止原因不会被误报。
3. 静止/低速感知：验证指定标记、错误标记、遮挡、远距离、背向和不同光照。
4. 探索中出现目标：验证暂停、取消 ACK、重复检测抑制和返航控制权。
5. 视觉盲区：把目标放在雷达已覆盖、摄像头尚未观察的分支，验证补查。
6. 闭环与恢复：走回环、短时遮挡和定位跳变，验证起点/目标一致性及失败退出。
7. 多个随机迷宫和目标位置重复实验；仿真与实机分别统计，不能用仿真成功替代实机完成。

当前交付为组件选择与设计依据，尚不构成 ROS 集成、仿真通过或实机实验完成的证明。
